We are moving from local prototypes to live cloud infrastructure. In standard software engineering, deploying a monorepo is where 70% of teams blow up their pipeline. Why? Because **standard cloud platforms do not understand workspace symlinks.**

If you tell a cloud server to deploy `apps/api`, it will look inside `apps/api/package.json`, see `"@carshop/db": "workspace:*"`, search the local folder, fail to find it, and throw a fatal `MODULE_NOT_FOUND` panic.

To conquer this, our deployment topology operates on  **Root-Level Orchestration** . The cloud platforms pull the *entire* monorepo, install from the root, and we use Turborepo's `--filter` flag to surgically compile only the target app.

```
                  ┌──> [ Vercel ]  ───────> ( Next.js Web App: Edge Network )
[ GitHub Main ] ──┼──> [ Render ]  ───────> ( Node.js API + Managed PostgreSQL )
                  └──> [ Expo EAS ] ─────> ( iOS .ipa / Android .aab Cloud Compilers )
```

# EXECUTION ORDER 06: The Continuous Delivery Engine

### Task 1: The Master Gatekeeper (`.github/workflows/ci.yml`)

Before any code is allowed to touch your cloud servers, it must pass the automated GitHub PR Gatekeeper.

Create `.github/workflows/ci.yml`:

**YAML**

```
name: Aurora Gatekeeper

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  verify-pipeline:
    name: Typecheck, Lint & Build
    runs-on: ubuntu-latest

    steps:
      - name: Checkout Workspace
        uses: actions/checkout@v4
        with:
          fetch-depth: 2 # Required for Turborepo git-diff calculations

      - name: Install pnpm
        uses: pnpm/action-setup@v3
        with:
          version: 8

      - name: Setup Node.js Environment
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'pnpm'

      - name: Install Workspace Dependencies
        run: pnpm install --frozen-lockfile

      - name: Forge Relational Client
        run: pnpm --filter @carshop/db generate

      - name: Execute Parallel Verification
        run: pnpm turbo run build --dry=false
```

### Task 2: Deploying the Backend & Database (Render / Railway)

Because you are operating bare-metal without Docker, **Render.com** (or Railway.app) is your target PaaS.

1. Create a live **PostgreSQL** instance on Render. Copy the provided `Internal Database URL`.
2. Create a new **Web Service** connected to your GitHub repository.
3. **CRITICAL ARCHITECT OVERRIDE:** Do *not* set the Root Directory to `apps/api`. Leave the Root Directory completely blank (defaults to repository root).

Configure the exact Render build variables:

* **Environment:** `Node`
* **Build Command:**
  **Bash**

  ```
  pnpm install && pnpm --filter @carshop/db generate && pnpm --filter @carshop/api build
  ```
* **Start Command:**
  **Bash**

  ```
  pnpm --filter @carshop/api start
  ```
* **Environment Variables to Inject:**

  * `DATABASE_URL` = *(Paste your Render Postgres Internal URL)*
  * `JWT_SECRET` = `Production_Elite_Secret_Key_9981!`
  * `REFRESH_SECRET` = `Production_Refresh_Secret_Key_9981!`
  * `NODE_ENV` = `production`
  * `PORT` = `10000` *(Render's default mapped port)*

*(Once deployed, copy your live API URL, e.g., `[https://carshop-api.onrender.com/api/v1](https://carshop-api.onrender.com/api/v1)`).*

### Task 3: Deploying the Storefront (Vercel)

Vercel owns Next.js and handles Turborepo natively, but we must protect your build minutes from **The Monorepo Trap** (rebuilding the website when a developer only edited the mobile app).

1. Import your GitHub repository into  **Vercel** .
2. Set **Framework Preset** to `Next.js`.
3. Set **Root Directory** to `apps/web`.
4. Expand  **Build & Development Settings** :
   * **Override Build Command:**
     **Bash**

     ```
     cd ../.. && pnpm turbo run build --filter=@carshop/web
     ```
   * **Ignored Build Step (The Money Saver):**
     **Bash**

     ```
     npx turbo-ignore
     ```
5. **Environment Variables to Inject:**
   * `NEXT_PUBLIC_API_URL` = `[https://carshop-api.onrender.com/api/v1](https://carshop-api.onrender.com/api/v1)` *(Your live Render API URL)*

### Task 4: The Mobile Cloud Factory (Expo EAS)

Your web storefront and API are live. Now we program the cloud to manufacture native smartphone binaries.

Install the Expo Application Services CLI globally and login:

**Bash**

```
npm install -g eas-cli
eas login
```

Navigate into `apps/mobile/` and initialize the cloud project:

**Bash**

```
cd apps/mobile
eas build:configure
```

This generates `apps/mobile/eas.json`. Replace its contents with our strict production matrix:

**JSON**

```
{
  "cli": {
    "version": ">= 7.0.0"
  },
  "build": {
    "development": {
      "developmentClient": true,
      "distribution": "internal",
      "env": {
        "EXPO_PUBLIC_API_URL": "http://10.0.2.2:5000/api/v1"
      }
    },
    "preview": {
      "distribution": "internal",
      "env": {
        "EXPO_PUBLIC_API_URL": "https://carshop-api.onrender.com/api/v1"
      }
    },
    "production": {
      "autoIncrement": true,
      "env": {
        "EXPO_PUBLIC_API_URL": "https://carshop-api.onrender.com/api/v1"
      }
    }
  },
  "submit": {
    "production": {}
  }
}
```

To trigger your first cloud compilation for Android (generates an `.apk` you can install right now) or iOS, execute from inside `apps/mobile`:

**Bash**

```
eas build --platform android --profile preview
```
